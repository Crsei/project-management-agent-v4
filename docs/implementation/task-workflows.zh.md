# 任务工作流与节点画布（第一版）

日期：2026-10-31。用户要求预制工作流、画布节点与一次授权后的自动交付。本模块是既有任务代码交付的编排，不恢复 v3 业务执行计划，不增加角色、业务审批或任务完成规则。对应 INV-01/03/05/13/14/15/20、SC-03/12/13/14/20、INF-05/06/07 的部分路径。

## 数据与授权决策

- 任务 Markdown 仍是需求权威；执行固定 task revision、项目目录、仓库身份、工作流发布版本、Provider、模型、测试命令及授权。后续编辑不能污染正在运行的快照。
- 工作流定义（草稿与不可变发布版本）、运行记录、节点记录与 Chat 会话分开建模。第一版复用 Agent 私有 SQLite 的独立命名空间、单进程所有权和 CAS；Chat 仅承载 Agent 节点执行，Git 副作用仍由原交付收据核对。
- 每个任务至多一条工作流运行，不能接管已经手动创建的交付。项目级模板通过当前任务的项目授权访问；发布/启动/恢复/人工确认需要原 planning.edit，不设新权限体系。
- 发布模板不授予执行权限。启动时明确授权 worktree 写入、测试命令，以及分别勾选自动 commit、push、Draft PR；服务端根据固定图再次校验，不因画布连线扩大权限。仓库名称须与实际 origin 一致。
- 认证头仅在进程内短期持有，不持久化；每次后台推进重查 PM 权限与任务版本。退出、会话失效、服务重启不会静默使用全局凭据。重启后需重新登录并显式恢复，原运行/节点身份不变，未知动作不会自动重放。
- 关闭页面不停止已授权的后台推进；暂停仅阻止后续推进，不冒充已经取消在途 Agent、测试或 Git 操作。人工确认节点仅是工作流继续确认，不是业务 Review 或任务完成批准。

## 第一版节点与限制

内置“需求分析”“开发并验证”“开发并交付”三套图。节点：任务输入、独立环境、Agent、测试、条件判断、commit、push、Draft PR、等待 CI、人工确认、结束。画布可拖动、连接、删节点/连线与配置；发布校验类型、连通性、必需参数、前置依赖与循环。只执行单令牌有向无环图，不支持并行、循环、任意脚本节点或自动合并/部署/完成。

分析模板也在独立 worktree 内运行只读 Agent。测试节点复用既有显式 shell 验证能力（120 秒上限），不是新增任意脚本节点。失败可走条件分支或停止，不自动无限重试。CI 按当前提交后台轮询，未发现检查不算通过；超时/远端版本变化/未知副作用转人工处理。评审仍展示真实 GitHub 证据，不伪造审批。

## 节点状态联动（2026-11-01）

新增[节点与任务状态联动](workflow-task-state.zh.md)。开发模板 v2 默认在 Agent 派发前自动申请进行中，交付模板在同提交的 CI 通过后人工确认待审核；画布可关闭或改为自动/人工模式。启动须单独授权状态联动。旧 v1、已发布图及运行不变。系统状态转换另存可信 revision 收据，不改需求快照，也不豁免人工编辑。

## 持久化提醒

**会话与持久化尚未统一设计，仍暂沿用 Agent Chat 基础存储。** 本次仅明确工作流数据与 Chat 的逻辑边界，不代表统一设计已经用户确认收口，也不是多实例 Runner、成员会话隔离或完整 G3 验收。

## 使用入口

保存任务后展开“任务工作流”，选择预制模板，或“复制为项目工作流”进入画布。编辑后先保存草稿，再校验发布版本。在没有既有运行/手动交付的新任务中，选择实际基准分支、已就绪的 Provider 和模型；“运行工作流”展示本次固定流程和分项授权，明确确认后由系统自动推进。暂停/恢复/人工确认在任务进度区域操作，Git 技术细节折叠展示；结束后的新评审可通过“核对 CI / 评审结果”更新证据快照。

## 明确选择本机隔离验证（2026-11-08）

- 新增 `builtin-canvas-local` 预设，旧模板和省略 `verification` 的历史请求仍使用原 GitHub CI 门槛；不把缺失检查当成功。新预设保留开发、测试、提交、上传、Draft PR 及任务待审联动，最终门槛为绑定提交的本机验证，不自动验收、合并或部署。
- 已暂停且停在云端检查的画布可明确确认 `use-local`，应用服务按版本 CAS、当前权限、任务版本、仓库及干净目录核对。原 input 不改写，原图和失败 CI 节点记录保留在 `localSwitch` / 原节点 ID；新增独立验证节点，之后另行恢复执行。未知副作用、失败开发、目录或任务漂移不能借此跳过。
- `verify-local` 仅处理已测试且有 Draft PR 的干净精确 HEAD；最终验证从不可变 Git blobs 复制源码，执行前后重核工作树、任务权限、版本及 PR HEAD。保存执行器版本、提交、指纹、时间、退出码、测试统计与日志摘要，不伪造 GitHub checks；失联结果不自动重跑。
- 当前执行器仅支持 Linux / Node 24、UTF-8 源码、无外部依赖、`node --test ...` 的 `npm test` 项目。使用一次性目录及 bwrap 的独立网络/进程/挂载空间，不挂载项目、用户 home、PM 数据、凭据或 `.git`；只开放沙箱回环网络以验证 HTTP。禁止联网安装依赖；上限 1000 文件/16 MiB、120 秒、1 MiB 输出及 Node 256 MiB 堆。未安装验证器或不支持的项目明确阻止，不降级为宿主执行。
- 退出成功且 TAP 汇总存在、测试数大于零、全部通过、零跳过/取消/todo 才通过。测试覆盖是否充分仍须按验收标准审查，不把计数或 Run 成功当成生产就绪。
- 本机方式不依赖 GitHub 云端计算，但不会自动更改仓库 Actions 配置、账单或预算；已有自动触发的云端 workflow 应由维护方单独禁用，避免额外排队/费用。Provider 开发调用仍可能消耗额度。
- 会话与持久化仍暂沿用 Agent Chat 保存方式，尚未完成统一设计收口。

### 修复后重新验证（2026-11-09）

`retry-test` 是明确确认后的新测试尝试，不是改写失败或自动重试。仅适用于本机验证预设中已结束开发、测试明确失败、尚未提交、没有未知副作用的原运行；原 HEAD 必须仍为已登记基线，代码指纹必须与失败测试不同。确认时重查权限、任务版本、目录、仓库和原分项授权，保存原图及完整失败测试到 `testRepairs`，保留原失败节点，再创建独立测试节点并保持暂停。另行继续时核对确认的精确指纹，执行原完整测试，成功后才能提交、上传和检查 Draft PR；每次失败独立保留，最多允许 5 次明确登记，不重复 Agent 开发或建立替代任务。画布只代理自己拥有且已暂停的原子运行，不能接管其他任务，也不会因此完成业务验收。
