### 1.0 本轮用户修订：新增许可默认 full access

本节优先于下文原规划中的新增权限／审批建议：

1. 本计划**新增**的操作许可、Execution Grant 策略和审计联动均默认 `full`／`audit-only`；只记录决策与非阻塞提醒，不要求用户逐次选择放行，不新增审批等待、操作许可门槛或通过开关才能使用的能力。
2. 新 Execution Grant 是服务端自动生成的执行来源／策略记录；不能成为第二层 ACL。新记录的范围、风险、有效时间用于证据和提醒，不凭这些新增字段阻断已有合法操作。新的授权策略 UI 只读展示，不新增允许／拒绝按钮。
3. 既有身份认证、PM 当前成员／项目权限、OAuth 身份建立和现有明确委托、撤权、服务认证、目录身份、revision／CAS、幂等及 unknown 禁止盲目重派继续强制执行。`full` 不等于匿名访问或跨用户／项目扩权；不静默改写现有部署的显式审批配置。
4. 原 B2／B4 中对**新增** grant 范围／过期的拒绝验收改为“自动 full 放行、记录并提醒”；伪造身份、借用其他执行记录和既有授权撤销仍须拒绝。原 D 的新增安装策略默认 full，不增加二次业务同意；已有 OAuth 身份认证不被插件绕过。
5. 审计是证据，不是新的操作批准步骤；原有保证提交／恢复一致性的事务和 journal 不降级。提醒记录写入失败不得假称已记录，亦不改变原业务收据或引发重派。

## 3. 工作包 A：执行结果与撤权安全

### 3.1 两个正交维度

执行事实仍使用以下五态；可见性单独按当前请求计算，不在撤权时覆盖执行事实。

| 执行状态 | 证据与含义 | 有权用户界面与动作 |
| --- | --- | --- |
| `pending_approval` | 已登记意图，等待有效审批，未派发 | 审批卡；审批绑定原参数摘要及原 operationId |
| `running` | 已进入执行，最终结果未确认 | 进度卡；取消只阻止后续动作，不声称回滚 |
| `succeeded` | PM 已提供匹配身份的权威提交收据 | 成功卡及授权可读 receipt／revision |
| `failed` | 已证明未派发，或 PM 权威结果证明未成功 | 失败卡；修正后是否再次执行由显式决策和当前授权决定，不自动换键 |
| `unknown` | 已可能派发，无法确认提交结果 | 待核实卡；禁用重试／再次执行，仅提供原操作核对 |

候选可见性投影：`visible`／`redacted`／`unavailable`，最终字段名由 T1 固化。`redacted` 表示当前主体不能读取；`unavailable` 表示授权或结果查询暂不可完成，不冒充撤权或空记录。内部可以知道 `succeeded`，撤权用户仍只得到“内容已不可访问”；不得通过标题、状态、目标 ID、收据链接或错误正文旁路泄露。

状态转换规则：

- 明确发送前拒绝 → failed；已发出后网络断开、超时、401／403／404／409／429／5xx、响应无法解析或身份不匹配 → unknown，除非已取得匹配的 PM 权威结果。
- 不把所有 4xx 一律改成 unknown：真正的本地未派发拒绝可确定失败，可信 PM 的已记录拒绝也可确定失败；依据是执行证据而不是状态码。
- unknown 只能通过原操作证据转成 succeeded／failed，或保持未决；`not_found`、收据过期／丢失不能证明未执行。
- 一旦确认 succeeded，不因撤权、查询错误、较旧 SSE 或 generation 失败而降级。业务后续再变更也不能改写原收据。
- 崩溃时的 running 进入 unknown；取消已发出的操作不等于回滚。确认部分副作用时保持未决并展示授权可读的核对说明，不制造“安全重试”。

### 3.2 内部核对合同

建议在既有 PM 内部服务认证边界内增加最小只读核对能力，不让外部用户绕过 `/result`：

1. 派发前持久保存原 `operationId`、actor、明确 target、工具／参数摘要及已知命令关联；绑定原始受信来源。不能凭调用者新提交的 actor 或任意 operationId 建立核对权。
2. Agent 使用已有服务间认证基础，增加用途／audience／方法／路径约束，仅能核对原受理操作。撤销的是用户执行／读取委托，不删除内部原操作证据；核对能力不能执行命令、扩权、枚举其他操作或读取正文。
3. PM 根据原收据与幂等／恢复台账给出最小状态和可信关联；存在跨存储未完成恢复时返回未决。返回仅供内部使用，正文、参数、对象标题、diff、Cookie、token 均不包含。
4. 用户获取正文仍通过现有 PM 当前授权检查。内部状态更新不得把完整收据重新广播给失权订阅者。
5. 核对可在明确查询、服务恢复或受控恢复流程触发，只重复只读查询；任何必要的审计恢复复用已有受审计恢复入口，不把核对端点变成写入重放器。
6. 明确核对证据的保留期、备份／恢复、故障状态；无证据时保持 unknown，不能换 operationId 消除歧义。

### 3.3 逐条历史脱敏

- Session／当前委托本身无访问权时仍拒绝整段访问。只有“Session 可访问，但部分工具目标不可访问”才逐条占位，不把占位策略变成会话授权绕过。
- 服务端先裁剪再序列化：工具参数／结果／错误、PM changeSet、receipt、历史附件／链接、消息引用、完整输出快照、增量事件和订阅重连都适用。分页使用不泄露目标的稳定调用标识；计数／摘要不包含隐藏目标信息。
- 同一个结果涉及多个目标时必须按实际依赖集合复核，不能只验主 target。无法证明正文可分割时仅遮蔽该条／该轮受影响内容，不牵连其他可证明安全的历史。
- 已进入 assistant 摘要、压缩记录、Provider 原生续聊游标的 PM 内容也可能泄露。优先保留可证明的来源标签；无法安全清除原生上下文时，切断受影响的续聊链、以已过滤历史启动新 generation，不重放业务工具。
- 不能从用户已下载、已阅读或外部客户端持有的数据中“追回”正文。承诺范围是撤权后的服务端新响应、流、恢复和新模型输入；外部缓存须明确列限制。
- 权限服务不可用时不放行缓存正文；返回可重试的读取不可用，不将数据库原记录改成失败或删除。

具体出口清单须进入 T5／T6 的覆盖表：`/calls`、PM core diff、Chat history／generation metadata、Chat SSE、native-output SSE／command tail、原生工具 input／output 副本、fork／transfer／regenerate／continue、标题生成／压缩摘要、MCP thread_read／send、MCP App 历史 HTML／工具结果、浏览器驻留与 sessionStorage 引用、私有备份及原生 continuation。明确失权须清除当前 UI 缓存，不用旧 snapshot 兜底；备份仍作为含敏感信息的私有副本保护，不能宣称“撤销 token 后备份正文已脱敏”。

### 3.5 A 验收场景

- **A1 五态与未派发拒绝**：逐态验证 API、持久记录、工具返回、SSE 和实际卡片；本地拒绝没有 PM 请求／副作用；unknown 卡不出现失败图标或可执行重试。
- **A2 提交后撤权**：在真实隔离 PM 中执行写入，写入 succeeded 收据后、响应前撤销委托并返回 403。Agent 先保留 unknown，再由内部核对确认 succeeded；业务只修改一次，失权用户所有入口只返回安全占位。
- **A3 未确认与竞争**：发出后断网、各类 4xx／5xx、非法响应、PM 已提交但 SQL 收据尚未补齐、取消／撤权／审批竞态；只有有证据才能终结，核对不会二次执行。
- **A4 重启和幂等**：分别在派发登记后、PM 提交后、Agent 保存前重启；原键恢复。相同键异参数／异主体／异目标／异委托拒绝；同键同参数返回原事实，不返回后来对象状态。
- **A5 混合权限历史**：一个 Session 含五项目，撤销其中一项目。其余四项目列表／详情仍可读；失权项目参数、正文、错误、标题、receipt、diff、链接和引用全部不可读；多目标调用不漏次要目标。
- **A6 流与模型边界**：撤权前连 SSE，撤权后继续订阅、断线重连、旧 cursor、慢消费者快照、复制／导出和下一轮生成；检查真实网络帧和 Provider 输入，不仅检查 DOM。已有外部下载不承诺撤回。
- **A7 核对安全**：外部 token、普通 PM cookie、伪造 actor、其他 operationId、错误 audience、重复／过期服务签名均不能借内部机制读正文或执行命令；网关不暴露内部路径。
- **A8 旧状态与迟到事件**：旧 failed 不直接批量改 succeeded；证据不足保留待核实。成功后收到旧 running／unknown 帧不回退；授权读取失败不修改业务结果，generation 结束不结束未核对业务事实。

恢复还须覆盖永久删除：当前 `agent-chat-tools.ts` 的 `pm_delete_task` 恢复存在返回未决的保守分支。T2 必须说明原 journal／tombstone 是否足以证明原删除；证据不足继续 unknown，不能再次删除或以当前对象不存在推断成功。

## 4. 工作包 B：不可变 TurnContext 与执行委托

### 4.1 模型与受理流程

保留用户提出的最小逻辑结构，作为受理后的服务端快照；具体 schema 版本字段在 T8 确定：

```ts
type TurnContext = {
  threadId: string;
  messageId: string;
  pmReferences: Array<{
    workspaceId: string;
    projectId: string | null;
    entityId: string;
    revision: string;
  }>;
  executionGrantId?: string;
};
```

这里的 `messageId` 建议明确指**已受理的输入用户消息 ID**。现有 generation 的 `messageId` 常是 assistant 输出消息 ID，frontend-tool continuation 还可让多个 generation 共享该输出 ID；T8／T14 必须显式映射输入消息、输出消息与 generation，不能直接重命名旧字段或以 messageId 唯一约束整轮。PM 文档与任务沿用现有 `kind/id` 引用区分；若公开形状统一为 `entityId`，需定义文档身份映射，不丢引用类型或工作区／项目联合身份。

约束：

1. Session 拥有消息、Provider、执行目录和历史，不新增“Session 当前 PM 项目”。PM 引用可以跨已授权项目／工作区，但每条引用必须独立校验真实归属。
2. Composer 草稿可编辑；发送受理时由服务端验证 thread／message 身份、引用读取权限、实体与 revision，再与消息稳定关联并冻结。消息受理成功后上下文不可原地修改。
3. 引用 revision 必须能精确说明模型实际获得的版本。旧 revision 无法获取时拒绝注入并提示用户显式刷新，不静默改用最新版本。若已有历史服务不能读取该版本，选择复用私有不可变引用快照或拒绝该请求，不能临时另造全套 PM 历史库。
4. 重试提交同一消息 ID 必须核对原快照与内容摘要；不同输入不能覆盖。编辑／重新生成明确区分：内容改变产生新消息上下文；同内容新 generation 沿用历史上下文，但重新检查授权，过期 grant 不复活。
5. PM Context 只是证据，不限制／授予全部执行目标。调用另一个已获授权项目时仍显式 target；不能把所有引用并集自动授予写权限，也不能把无引用解释为无 PM 工具能力。
6. `executionGrantId` 只是受信服务端委托引用；客户端可请求使用既有授权，不能自封 actor／capabilities／target ceiling／审批豁免／有效期。授权上限与实时 PM 权限取交集。
7. 短期执行委托不是 OAuth token 本身，也不是新的成员 ACL。外部 OAuth consent 可作为来源，应用生成本次执行的受限绑定；本机普通请求也保留现有身份检查。PM 不可用不阻止无 PM 引用／工具的代码会话。
8. 每次工具真正执行、审批恢复、核对正文读取时重验；grant 过期／撤销不更改原收据，不自动重授。历史 TurnContext 永远不含 Cookie、Bearer token 或原生 CLI 凭据。
9. 重新生成若需要新的执行委托，新引用保存在该 generation 的不可变执行绑定中，不回写原 TurnContext；旧上下文中的 grant 只是当时证据。新授权仍不得复活旧审批或重放未决 operation。

### 4.2 Composer 与历史展示

Composer 上方增加 **“本次消息的 PM 上下文”**，副标题 **“仅作用于当前消息”**：

- 引用 chips 显示授权可读的项目／任务／文档和 revision；可添加、移除，发送前提示缺失／过期／无权读取，不把失败显示为无引用。
- 执行目录沿用当前 Session 环境，单独显示实际路径／Worktree；不随 PM 引用改变，不将目录当授权。
- 授权摘要单独显示“可读／可写目标范围、需审批动作、有效期／未取得执行委托”，来自服务端，不让用户通过文案编辑权限。
- 发送成功后清空本次引用草稿；下一条不自动继承。可显式“复用此消息引用”，重新校验，不复用历史授权。
- 消息历史显示当时冻结的引用及当前可见性；失权时使用 A 的占位策略，不能把历史 grant 当当前授权。
- 保留当前文本草稿、附件丢失提醒和离页保护；新增上下文草稿是否持久化由 T8 一并决定，不能暗中引入第二套保存协议。

### 4.4 B 验收场景

- **B1 跨项目且目录稳定**：同一 Session 的三条消息分别引用 A、B、C，含不同工作区同名／同实体 ID；执行目录不变。首次执行、原生 resume、portable、continue 都实际收到本轮正确引用及版本，历史不被最新 Composer 草稿覆盖；不因新引用仅进入一次性 system 而在续聊丢失。代码在 A 的目录不代表只能访问 A 的 PM 对象。
- **B2 授权交集**：客户端伪造 grantId、actor、过宽 target、capability；引用 B 却操作 C；审批后变更参数／过期／撤权。只允许当前身份、有效委托与 PM 当前权限交集内的显式动作；引用不能扩权。

- **B5 持久化与迁移**：在消息／上下文登记边界中断并重启，不出现已运行却无上下文的半记录；旧历史缺少字段保持未知、可读而非自动获权；备份恢复不复活授权。删除会话不级联删除 PM 收据／审计。

## 5. 工作包 C：统一关联链与 PM 命令审计

### 5.1 标识合同

不合并数据表；只建立可验证的关联。推荐每个 generation／执行根一个 `traceId`，同一 generation 内多工具共享 trace，各工具仍有独立 invocation／operation；新 generation 使用新 trace，以父关联定位原消息。最终基数由 T14 定稿。

| 标识／记录 | 权威与作用 | 不可替代的边界 |
| --- | --- | --- |
| threadId／messageId／TurnContext | Agent 会话和不可变消息证据 | 不代表 PM 项目归属或权限 |
| generationId／traceId | Agent 执行实例与跨服务根关联 | trace 不是幂等键，也不是授权凭据 |
| tool invocation ID | Agent 一次具体工具调用事件 | 不等于 PM 已提交 |
| operationId | 原业务操作及核对身份 | 同一逻辑操作不因超时、撤权、客户端重连而更换 |
| approval／executionGrantId | 服务端授权来源和本次上限 | 只引用有效证据，不复制令牌，不自动变成成功 |
| commandId／PM receipt | PM 命令及权威结果 | 只读查询未必有 commandId；多步操作需明确关联集合，不伪造一对一 |
| Business Change／revision | 实体的实际版本变化 | 无变更的成功查询／幂等重放不能制造新 revision |

边界要求：

- traceId 由受信接入服务签发或验证绑定；外部传入 trace 仅能作为受限关联提示，不允许借它选择 actor、读取别人历史或覆盖既有链。
- HTTP、MCP、CLI、原生 Provider 工具、审批、恢复、SSE 和授权可读 receipt 使用同一关联语义；原操作核对保留原 trace，不生成“第二次执行”。
- 外部客户端没有本地 Agent thread／message 时记录其受信来源与可选外部会话关联，不创建假 Chat 或强迫它先开一个目录型 Session；若当前网关必须绑定纯对话线程，T21 必须明确最小安全调整并保留既有隔离。
- 所有关联查询仍按当前主体、项目、审计能力和委托范围过滤，不能通过 trace 遍历到隐藏项目。
- commandId 继续接受已有业务 UUID 与 native SHA-256 字符串，不统一强改为 UUID。当前外部 MCP 直接调用使用 `mcp:<operationId>` 合成关联，不能新增指向真实 ChatGeneration 的强制外键；T14／T21 应将这种外部执行关联显式建模，而非伪造模型轮次。

### 5.2 审计增量

先盘点现有审计与命令入口覆盖，再扩展白名单字段：actor、可信委托来源／grant 引用、客户端类别、target、动作、原 operationId／commandId／traceId、预期及实际 revision、结果和安全错误码、记录时间。

- 参数仅保存经批准的字段／规范化摘要，不存原消息、正文、Cookie、token、密钥、完整路径或原始异常。低熵敏感值不能只靠普通哈希伪装脱敏。
- 请求／授权拒绝记录与业务已提交审计区分；没有实际变更不制造成功变更。一个 operation 可能拥有多条阶段记录，但只有原命令的权威业务结果。
- PostgreSQL 内事务与 Markdown journal 恢复分别保证；文件已提交、SQL 记录未完成时保留原身份并恢复记录，不能因审计写入失败重放文件动作。
- 外部文件编辑只有观测证据时，actor／source 保持 unknown；不能按临近时间或同 Session 猜测归因。
- 审计查询与正文变更历史分离；沿用已有 `audit.read` 与项目权限。保留期、恢复核验、清理权与访问范围必须在 T16 定稿，多用户正式发布前是门禁。

- **C2 重试与伪造**：断线核对保持原 operation／trace；新 generation 的 trace 不覆盖旧链；伪造 trace／grant／客户端来源不改变身份或查询权限；多命令调用不丢关联。
- **C3 原子边界与恢复**：命令拒绝、同键重放、并发 CAS、文件提交后审计中断、服务重启后恢复；业务修改一次、成功审计不重复，未决不伪报失败。
- **C4 脱敏与权限**：日志、审计、API、SSE、CLI 输出均无敏感正文／凭据；另一主体／项目失权／audit.read 缺失无法沿 trace 越权遍历。
- **C5 旧历史与观测**：旧记录无 trace 保持缺失，仅有确定关联才补链；外部磁盘编辑来源未知。备份恢复与保留期到期不会把缺失证据当作未执行。

## 6. 工作包 D：跨 Agent 可安装插件

### 6.1 标准核对与兼容策略

编制时已读取一手资料；网页是浮动文档，实施时须固定客户端版本、标准 schema 与测试环境，不能把文档现状当成本机安装能力。

| 来源 | 已核对的事实 | 规划约束 |
| --- | --- | --- |
| [Agent Plugins 1.0.0](https://agent-plugins.org/specification) | 已发布；根 `plugin.json`、`skills/`、`mcp.json`；v1 仅两种核心组件 | 标准包使用固定位置、规范 `$schema`；不添加自造顶层 capability／OAuth 字段 |
| [OpenAI 插件打包](https://developers.openai.com/plugins/build/plugins) | 描述 portable 根 manifest 与 Codex 兼容布局，安装能力因 surface 有差异 | 分别记录 Codex CLI／桌面实际目标与版本；不把 CLI 配置成功说成桌面安装通过 |
| [Claude manifest](https://code.claude.com/docs/en/plugins/manifest-reference) | 原生 `.claude-plugin/plugin.json` 与自身组件配置／验证规则 | 从同一源生成原生薄封装，不声称完全等同 portable schema |
| [OpenCode MCP](https://docs.opencode.ai/docs/mcp-servers/) | 原生 remote MCP、OAuth 发现／授权、配置格式不同 | 优先生成原生 MCP＋Skill 配置；确有缺口再加 JS／TS 插件 |
| [Pi 扩展文档](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/extensions.md) | TypeScript 扩展、工具注册、包入口；扩展拥有宿主 OS 权限 | 固定目标版本，交付最薄适配；不把社区加载器或扩展当隔离沙箱 |

规范特别限制：portable `mcp.json` 的 remote `url`／headers **不支持环境变量占位展开**；不得嵌入凭据。OAuth 发现、交互和凭据保存由客户端处理，不属于 v1 portable 配置。非回环 HTTP 不可作为标准远程地址。客户端加载时不在线拉 schema，应固定本地可识别 schema 做校验。

因此自托管实例地址采用显式安装配置生成具体 URL，或使用已确认的正式 HTTPS origin；不把 `${DOVSPACE_URL}` 填进 portable `url` 并宣称兼容。没有正式域名时不发布假地址。

### 6.2 最小产品结构

- **Capability Registry**：复用 PM 工具注册表／schema，为各通道导出名称、描述、输入、风险／能力要求和结果合同。工具数量以注册表实际输出为准，不固定复制“17 个”。审批策略仍由服务端拥有。
- **Plugin Gateway**：演进现有 `/mcp`、OAuth、`callPmTool()` 与 PM 应用入口；不增加业务数据库写者。工具发现不等于授权，插件声明 actor／target ceiling 不可信。
- **Plugin Distribution**：一份 `dovspace-pm` 能力／Skills 来源，生成 portable 与必要原生安装产物；客户端适配只做安装、配置、认证接入和协议映射。

建议在实现时选择一个清晰的插件源码目录；此处目录名是待创建交付物，不声称仓库已存在：

```text
plugins/dovspace-pm/
  plugin.json
  mcp.json
  skills/
    project-management/SKILL.md
    issue-management/SKILL.md
    task-planning/SKILL.md
  README.md
  LICENSE
```

适配源码和生成器放独立工程目录，产出 Claude／OpenCode／Pi 包。用户附件中的 `adapters/` 可以作为仓库构建资源，但不是 portable runtime 的发现组件；需要标准客户端扩展时使用规范要求的反向域名命名空间，不能自称标准支持任意 `adapters/` 自动加载。

Skills 必须描述真实可调用的能力：发现目标、读取精确版本、提出变更建议、显式授权／审批后写入、未知先查询原操作。任务规划默认只输出草稿，不暗中创建任务、越权确认或宣布完成。可复用现有 PM 分析 Skills 的规则，但不能把本机私有路径／内部工具写成外部插件依赖。

### 6.3 授权、审批与恢复体验

1. 安装不会复制本机 cookie，也不授予 PM 项目权限；客户端首次连接走现有 OAuth／S256 和用户同意，默认只读，写入范围需明确授权。
2. 继续验证 issuer／resource／audience、redirect URI、state／PKCE、token 过期／撤销与工具访问范围；令牌不能登录普通 PM／Agent API。无公网配置时外部访问明确不可用，不回退无认证。
3. 客户端原生确认不能替代 PM 审批。审批延迟／浏览器中批准后，客户端只能核对原 operationId 的状态；需确保审批可定位且不会因多次点击重复提交。
4. 客户端重启、认证失效、响应丢失后保存并核对原操作身份；客户端操作记录只持久化必要关联，不保存服务端凭据或无授权正文。
5. CLI 复用现有登录／会话机制，不把其他客户端 OAuth token 偷换成普通 PM token；若提供 OAuth 委托专用 CLI 路径，必须通过同一网关合同，而非放宽普通 API 认证。
6. 生命周期写工具按当前部署审批策略执行；验收使用显式 `ask` 验证审批，另核对现有 `auto-approve` 不绕过 PM 权限。不新增秘密自动批准入口。

每个客户端记录精确版本、OS、安装方式、包摘要、授权身份类别、测试时间和证据路径，不能用“其他客户端应该类似”代替：

## 9. 数据迁移、切换与恢复

1. **盘点后切换**：列出 Agent 旧五态记录、native output 投影、消息引用、grant／token、PM 收据／audit／journal 和版本；先做一致备份，不删除 Session 来绕过新合同。
2. **旧 failed 纠偏**：只对能证明来自问题分支的记录按原身份核对；没有原始证据的记录不得批量改 succeeded／failed，可标“历史结果未核实”。保留纠正来源，不清空原始审计。
3. **旧 TurnContext**：只有可信原消息引用及精确 revision 才迁入；其余保持旧历史／上下文未知，不拿当前实体补历史，不凭历史 grant 重新授权。
4. **旧 trace／审计**：不编造 trace 或 actor；只补能证明的关联，现有收据 ID 不改。重复／恢复记录用既有幂等规则去重。
5. **撤权与恢复**：备份副本的授权失效规则继续保留，恢复不能复活 consent／token／临时 grant；恢复业务结果证据不等于恢复读取权限。
6. **一致发布**：PM、Agent、contracts／client 和 Web 的新语义一起验收；部署前有版本不兼容则拒绝相关新调用，不能退化到把 unknown 映射 failed 的旧路径。移除旧错误消费者，不长期保留双套合同。
7. **回滚边界**：先暂停本项目受影响的新派发，保留 unknown／收据／journal；只回滚兼容产物。数据库或不可逆格式变更不能只回滚二进制，更不能自动重放未决操作。优先前向修复，必要恢复使用独立目标及一致 checkpoint。
8. **插件生命周期**：包版本／schema／兼容客户端分开编号；更新不能自动扩大 PM 权限；本地卸载不删除业务审计，撤销授权单独可见。
