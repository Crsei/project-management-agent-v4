## 关系与顺序

- `draft:T2 depends_on draft:T1`；`draft:T3 depends_on draft:T2`；固定更新协议后接入 UI，再打通安全安装。
- `draft:T4 depends_on draft:T1`；`draft:T5 depends_on draft:T4`；发行材料协议是发布流水线的输入。
- `draft:T6 depends_on draft:T2/draft:T3/draft:T4/draft:T5`；整合后集中运行检查，不用各代理的局部结论代替集成验证。
- `draft:T7 depends_on draft:T6` 和发行门禁；不能把已实现功能或构建成功当作发布获准。
- 固定共享协议后，运行时/UI、打包/校验、发布流水线可并行；各自拥有独立文件，公共接口改变须先协调。
- `draft:M1`：更新能力完整且集成验证通过；`draft:M2`：两个原生版本与可见更新源交付；`draft:M3`：操作者完成真实 App 更新测试。均为候选里程碑，不是已创建业务记录。

## 发布前待办与阻塞

2026-11-12 实际执行 `node scripts/check-third-party-notices.mjs --release`：27 项 scoped integrity 检查通过，但以下四项 OPEN 导致退出码 1：`MISANS-GRANT`、`ASSET-ORIGINS`、`ARTIFACT-NOTICES`、`AGPL-SOURCE`。不能删除、跳过或把 preview 当例外绕过；关闭须有对应来源/授权和最终材料证据。公开仓库存在本身不足以关闭 AGPL 对应源码及应用入口验收。

计划保留上述全部候选，不擅自缩为只实现“检查更新”。公开发布被阻塞时仍完成可达的实现、验证与已授权源码推送，明确区分原生构建产物、draft Release 和客户端可见 Release。签名凭据不存在时不冒充 signed；不把 unsigned mac 作为完整自动安装验收。

本计划复用现有原生构建、精确材料校验、许可门禁、窗口离页保护和本地服务管理；不另建权限、会话或业务任务系统。若后续需要正式 PM 任务，由授权流程创建并把候选映射为真实 ID；此处仍为草稿，未发布、未派发业务任务。

## 操作者双版本测试

1. 安装包含更新能力的 `0.1.1-preview.1`，确认界面显示准确当前版本；使用独立测试数据，先备份，不以唯一业务数据测试升级。
2. 第二版尚未发布时检查：不得把历史版本、草稿或稳定渠道外不匹配版本误报为更新。
3. `0.1.1-preview.2` 完整材料通过门禁并发布后，再检查：显示准确目标版本、可执行下载及进度。
4. 下载后取消安装确认：保持旧版本及当前工作区可用，不隐式退出。
5. 确认重启安装：先处理未保存内容并正常停止服务；安装完成重新打开后显示第二版，核对登录、项目、文档与聊天数据。
6. 再次检查不能重复提示同版或降级。另测断网、下载失败、候选不兼容和停机失败；错误不能显示为“已是最新版”或“更新成功”。

两个版本可先全部构建；如果需要验证“发布前无更新 → 发布后出现更新”的完整过程，应在操作者安装基线并确认后才把第二版从 draft 发布。只验证从旧版识别新版时，可在两个版本都发布后手动安装第一版再检查。
