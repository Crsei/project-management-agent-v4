# Project management

1. Discover the currently advertised PM tools and authorized business targets; never invent workspace/project IDs. MCP uses its tool discovery and `pm_list_workspaces`; CLI uses `pnpm pm plugin tools` and `pnpm pm plugin workspaces`. A Session or code directory does not belong to a PM project and grants no PM authority.
2. For every business call other than discovery, pass an explicit `target` with `workspaceId` and `projectId` (null only for an authorized workspace-scoped action), plus the registered `arguments`. Read with `pm_query` / `pm_read`; follow pagination and distinguish summaries from full bodies.
3. Keep the exact returned revision with the record. Read the required body pages before proposing a change. If a requested historical revision cannot be read, report that limitation; do not label the current body as an old snapshot.
4. Perform the user's requested changes using only tools actually advertised by the server. New plugin operation policy is full access / audit-only: do not invent a second allow/deny prompt, ACL, or approval wait. Existing OAuth identity/consent, PM membership/project permissions, revocation, exact revisions and explicitly configured deployment approvals still apply. Never bypass them.
5. Before dispatch, choose one UUID `operationId` for the logical operation and retain it. Keep its exact tool name, target and arguments unchanged for original-result recovery. Server-issued `traceId`, invocation/command IDs and receipts are evidence, not credentials; preserve them verbatim, including non-UUID command IDs.
6. Preserve `pending_approval`, `running`, `succeeded`, `failed` and `unknown` exactly. A timeout, 403 after dispatch, invalid response or client restart does not prove failure. For unknown/running/approval recovery, MCP uses `pm_get_operation_result` with the **original** operationId; CLI uses `pnpm pm plugin result --file "$ORIGINAL_REQUEST_FILE"` under the original identity/origin. Never call the business write again, mint a replacement key, switch actor/profile or infer success from the object's current state. Missing evidence remains unknown. If the result query is unavailable, stop recovery and report the missing capability, rather than replaying.
7. Existing PM approval, when explicitly configured, is server-owned; a client confirmation cannot replace it. Follow only the authorized approval link supplied by the server, then query the original operation. Do not approve a different parameter set.
8. Treat visibility independently of business outcome. Redacted/unavailable results cannot be reconstructed from cached titles, arguments, errors, receipts or other project history. Recheck current access for subsequent reads. Previously downloaded external-client history cannot be recalled by the server.
9. Report the actual business result and its authorized evidence. A successful tool, model turn or code run is not proof that a WorkItem is complete. Do not change task state unless the user requested the real lifecycle action.

## Transport, paging and lifecycle

- CLI business dispatch is `pnpm pm plugin call --file "$ORIGINAL_REQUEST_FILE"` with `{operationId, name, target:{workspaceId,projectId}, arguments}` matching the advertised business schema. `pm_list_workspaces` and `pm_get_operation_result` are MCP gateway control tools, not CLI business `name` values. Protect original request/result files; never add credentials, actor claims or invented Chat associations.
- A zero exit from `plugin call/result` is not business success. Save the response privately and gate an authorized dependent action with `pnpm pm plugin check --file "$PRIVATE_RESULT_FILE"`: only `visibility=visible`, `status=succeeded`, a present `result` and `error=null` pass. This is a local check, not dispatch. Other outcomes/visibility stop continuation; a redacted historical success stays successful but its body cannot be shown.
- `pm_query` starts with `after:null`, `limit:1..20`; pass returned `nextCursor` unchanged as `after` until null. `pm_read` uses `id`, `bodyOffset` (initially 0), `bodyLimit:1..12000`; continue `nextBodyOffset` as `bodyOffset`. Each next page or fresh read gets a new UUID operationId and a separate request file; never edit the original request saved for recovery. Compare revisions before combining pages; partial/failed paging is not an empty or complete result. Other resource families use their own advertised pagination schema.
- For a requested task state change, read `pm_read_workflow({projectId})` and the current task. Use returned state IDs/categories and allowed transition edges, not guessed `done`/`completed` labels. Check current acceptance evidence for completion; call `pm_transition_task` with `{id, revision, status}` only for the requested valid transition, then freshly read back the task. A conflict requires fresh evidence/replanning, not silent overwrite.

For task execution, read the advertised `pm_task_brief` with `{projectId, taskId, revision, stage, bodyOffset, bodyLimit}` at the exact current revision; nullable page fields follow the schema. Continue `brief.task.nextBodyOffset` as `bodyOffset`; preserve acceptance, constraints, non-goals and gaps. `dispatchable=false` or remaining truncation is not permission to discard requirements. `pm_search_knowledge` takes `{projectId, taskId, revision, query, projectIds, limit, cursor}`: explicit nonempty query, `projectIds:null` for the current project, `limit:1..20`, `cursor:null` initially, then `knowledge.nextCursor` as `cursor`. Extra project IDs must be explicit and authorized. Preserve source revisions and `needs_review`; reread candidate sources with `pm_read` using source `entityId` and truncation `nextBodyOffset`, rejecting mixed revisions. Neither read starts execution or authorizes a business transition. An installed Skill is not proof that the current Provider loaded it; only claim capabilities actually available this turn.

Use `issue-management` for issue-specific edits and `task-planning` for a non-writing plan draft. Never execute arbitrary source files, shell commands or market plugins as a substitute for PM tools.

## Extended resources

Use only advertised resource-specific tools for collaboration, members/teams/capacity, documents/artifact versions, planning records, automation and integrations. Their current authority, private-owner scope, revisions and confirmation fields remain binding; a broad catalog is not authority for unrelated changes. Artifact references are immutable versions, not arbitrary local paths; preserve external-send receipts and never resend an unknown webhook merely because no response arrived.

`pm_automation_validate` validates without saving/executing; saving a draft does not run it. `pm_automation_test` **really executes** the saved snapshot and may have external side effects: do not interpret a request for a harmless preview as permission to test. `pm_automation_candidate_preview` does not mutate business objects or dispatch but retains audit/preview receipts; applying the reviewed token/selected prerequisite closure is a separate requested action. Recover unknown work via original operation/execution/receipt identities, not a new test/apply.

Evidence, Submission and Review are separate facts. PM models may read human Review but cannot issue human approval; do not invent a model review-approval tool or bypass the operator's explicit human confirmation. Account secrets, Provider credentials, Agent host/session/terminal administration and arbitrary filesystem paths are not PM model tools. PM authentication does not authorize those operator surfaces; the session/persistence unification design is not finished.
